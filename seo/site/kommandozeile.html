Kommandozeile, Crawler und CI

Derselbe Regelkatalog, der im Browser läuft, läuft auch in der Kommandozeile: über einzelne Dateien, über eine ganze Domain und in der CI-Strecke, wo er den Build scheitern lässt, bevor ein Fehler live geht. Ohne Fremdpakete, ohne Konto, ohne Anmeldung.

Eine Quelle für beides. Der Katalog liegt in einer einzigen Datei. Browser, Kommandozeile und CI lesen dieselbe.

Loslegen

Drei Befehle, mehr braucht es nicht.

Voraussetzung ist Node ab Version 18. Sonst nichts: keine Abhängigkeiten, kein Installationsschritt, kein Konto.

Einzelne Dateien prüfen
seo-rank pruefen site/index.html seo-rank pruefen "site/*.html" --stufe kritisch seo-rank pruefen https://beispiel-domain.de/ --ausfuehrlich

Nimmt Dateien, Muster mit Sternchen oder Adressen. Bei Adressen wird genau einmal abgerufen.

Eine ganze Domain crawlen
seo-rank crawl https://beispiel-domain.de/ --max 500 seo-rank crawl https://beispiel-domain.de/ --format json --aus bericht.json

Folgt internen Verweisen, hält sich an die robots.txt, macht Pause zwischen den Abrufen und prüft jede Seite gegen den vollen Regelsatz. Dazu kommen die Befunde, die man nur beim Abruf sieht.

Ein Dokument ausmessen
seo-rank analyse site/index.html seo-rank analyse https://beispiel-domain.de/ --ausfuehrlich

Kein Urteil, nur Messwerte: Umfang, Textanteil, Satzlänge und Lesbarkeit, Titel- und Beschreibungsbreite in Pixeln, Anzahl und Art der Verweise, die Gliederung der Überschriften, das Wortfeld mit Dichte und Vorkommen, dazu die Punktzahl je Gruppe. Wer wissen will, warum eine Punktzahl so ausfällt, sieht hier die Zahlen, auf denen sie steht.

Den Regelsatz durchsuchen
seo-rank regeln seo-rank regeln hreflang seo-rank regeln --format json

Listet alle 158 Regeln mit Kennung, Stufe und Gruppe. Die Kennungen sind es, die man in --nur und --ohne einträgt.

Nur beim Crawl

Was der Crawl zusätzlich sieht.

Diese acht Befunde lassen sich aus einem eingefügten Quelltext nicht ableiten. Sie entstehen erst, wenn die Seiten tatsächlich abgerufen und miteinander verglichen werden.

  • Weiterleitung und Weiterleitungskette. Ein Sprung ist ein Hinweis, mehrere hintereinander sind ein Problem: jeder kostet Zeit, und ab dem fünften bricht Google ab.
  • Langsame Antwort. Gemessen wird die Zeit bis zur vollständigen Antwort, einschließlich aller Weiterleitungen. Ab 2.500 ms gilt sie als zu langsam.
  • Interner Verweis zeigt ins Leere. Verlinkte Adressen, die mit einem Fehler antworten, mitsamt der Seiten, von denen aus verlinkt wird.
  • Derselbe Titel auf mehreren Seiten. Verglichen wird nach kanonischer Adresse, damit dieselbe Seite unter zwei Adressen nicht fälschlich als Doppelung gilt.
  • Dieselbe Beschreibung auf mehreren Seiten. Meist ein Zeichen dafür, dass das System eine Standardbeschreibung einsetzt.
  • Adresse zeigt kanonisch auf eine andere Seite. Interne Verweise sollten gleich auf die maßgebliche Adresse zeigen.
  • Seite ohne eingehenden Verweis. Erreichbar, aber von keiner anderen geprüften Seite verlinkt.
  • Keine HTML-Antwort. Die Adresse liefert etwas anderes und wurde deshalb nicht gegen den Regelsatz geprüft.

In der CI-Strecke

Den Build scheitern lassen, bevor der Fehler live geht.

Der Rückgabewert ist 0, solange nichts ab der gesetzten Stufe gefunden wird, sonst 1. Damit reicht der Aufruf allein schon aus, um eine Strecke zu stoppen. Für GitHub liegt eine fertige Action dabei.

.github/workflows/seo.yml
- uses: actions/checkout@v4 - name: Seiten prüfen uses: seo-rank.me/seo-rank.me@v1 with: ziel: "site/*.html" stufe: wichtig format: junit bericht: seo-rank-bericht.xml

Die Ausgabe im Format junit lesen die üblichen CI-Systeme als Testfälle: jede Regel wird zu einem Fall, jeder Befund zu einem Fehlschlag. Zusätzlich schreibt die Action eine lesbare Zusammenfassung in den Lauf.

Ein Rat aus der Praxis

Fangen Sie mit --stufe kritisch an. Sonst scheitert der erste Lauf an dreißig Hinweisen, und die Strecke wird abgeschaltet statt repariert. Wenn die kritischen Befunde weg sind, ziehen Sie auf wichtig nach.

Das Abrufrelais

Eine Adresse prüfen statt Quelltext einfügen.

Ein Browser darf fremde Adressen nicht abrufen. Ein Server darf es. Das Relais tut genau das und sonst nichts: es holt eine Adresse und gibt zurück, was es bekommen hat — Kopfzeilen, Weiterleitungskette, Quelltext. Geurteilt wird weiter im Browser, mit demselben Regelkatalog wie bei eingefügtem Text.

Das ist eine Entscheidung gegen die naheliegende Bauweise. Wer die Regeln in den Server legt, hat sie zweimal; zwei Fassungen derselben Bewertung laufen auseinander, und dann stimmt eine von beiden nicht mehr.

Welches Relais benutzt wird —

Gilt für diesen Reiter und ist beim Schließen weg. Leer lassen setzt auf die Voreinstellung zurück.

Selbst betreiben

node cli/relais.mjs 8124
# dann im Feld oben eintragen:  http://localhost:8124
  • Zwei Fassungen, ein Vertrag. cli/relais.mjs läuft überall, wo Node läuft. backend/http-functions.js ist dieselbe Sache für Wix Velo: Datei ins Backend legen, veröffentlichen, fertig. Beide antworten auf /holen?url=… mit demselben JSON.
  • Ein Relais ist ein Tor. Ein Dienst, der jede genannte Adresse abruft, öffnet das Netz, in dem er steht. Abgewiesen werden localhost, alle privaten Bereiche, 169.254.169.254, Namen ohne Punkt und alles außer http und https. Die Node-Fassung prüft zusätzlich, wohin ein Name zeigt — vor jedem Sprung, auch nach einer Weiterleitung.
  • Fehler kommen als Antwort, nicht als Absturz. Auch ein misslungener Abruf antwortet mit 200 und nennt den Grund. Wer 500 zurückgibt, lässt den Browser nur „Failed to fetch“ sehen.
  • Zehn Werkzeuge können laden. Seiten-Prüfer, Domain-Check, robots, Sitemap, Strukturdaten, hreflang, Stichwort, WDF·IDF, Werkbank und die Snippet-Vorschau. Wo geladen wurde, steht es daneben.

Ohne Relais bleibt alles wie zuvor: Quelltext einfügen, und nichts verlässt das Fenster. Der Unterschied wird auf jeder Seite genannt, die abrufen kann.

Alle Schalter

Was sich einstellen lässt.

Schalter der Kommandozeile mit Standardwerten
Schalter Wirkung Standard
--format Ausgabeform: text, json oder junit text
--stufe Ab welcher Stufe der Rückgabewert 1 wird wichtig
--nur Nur die genannten Regeln prüfen alle
--ohne Die genannten Regeln auslassen keine
--ausfuehrlich Die gefundenen Stellen mit ausgeben aus
--aus Ausgabe in eine Datei schreiben Bildschirm
--max Höchstzahl der Seiten beim Crawl 200
--tiefe Höchste Klicktiefe beim Crawl 5
--verzoegerung Pause zwischen den Abrufen in Millisekunden 250
--ohne-robots robots.txt übergehen, nur für eigene Server aus

Häufige Fragen

Zur Kommandozeile.

Warum ohne Fremdpakete?

Weil ein Prüfwerkzeug, das selbst dreihundert Pakete nachlädt, schlecht zu einer Website passt, die keinen einzigen fremden Server aufruft. Der HTML-Parser, die Selektoren und die Ausgabe sind eigener Code, abgesichert durch einen Selbsttest.

Sind die Ergebnisse dieselben wie im Browser?

Ja, und das wird geprüft. Der Selbsttest schickt dieselbe Beispielseite durch beide Wege und vergleicht die Zahlen. Weichen sie ab, scheitert der Test.

Wie misst die Kommandozeile Pixelbreiten ohne Browser?

Aus einer Tabelle der Zeichenbreiten von Arial, die einmal im Browser gemessen wurde. Die Abweichung gegenüber der echten Messung liegt unter einem halben Prozent.

Belastet der Crawler fremde Server?

Er hält sich an die robots.txt, ruft eine Adresse nur einmal ab, macht standardmäßig 250 Millisekunden Pause und meldet sich mit einer eindeutigen Kennung. Wer schneller crawlen will, tut das auf eigenen Servern.

Kann ich eigene Regeln ergänzen?

Ja. Der Katalog ist eine Liste aus Objekten mit einer Prüffunktion. Eine neue Regel dort ergänzen, den Erzeuger für den Regelsatz laufen lassen, fertig: sie gilt danach im Browser, in der Kommandozeile und in der CI.

Was ist mit Seiten, die ihren Inhalt erst per Skript aufbauen?

Der Crawler führt kein JavaScript aus, wie die meisten Crawler von Suchmaschinen im ersten Durchgang auch nicht. Genau dafür gibt es die Regel inhalt-nur-per-skript: sie meldet, wenn im ausgelieferten Dokument kaum Text steht.
